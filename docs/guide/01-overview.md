# 01 总览

## 一句话

MUI 是一个 **Minecraft 1.7.10 的界面库**：页面是 HTML + CSS，数据和逻辑留在 Java，
库负责解析、排版、绘制和输入，把结果送进游戏自己的渲染管线。

```html
<div class="mui-panel">
  <div class="mui-title">Furnace</div>
  <div class="mui-row">
    <div class="mui-progress"><div class="mui-progress-fill" style="width: 62%"></div></div>
  </div>
</div>
```

```java
Mui.open("screens/furnace.html");
```

这段 HTML 里的每一个概念——`display: flex`、`padding`、`border-radius`、百分比宽度——
都是 MUI 自己算出来的，而不是浏览器的。

## MUI 是什么

| 你会写的东西 | MUI 做什么 |
| --- | --- |
| HTML 文件 | 容错解析成文档树（DOM） |
| CSS 文件 | 选择器匹配、层叠、继承、简写展开、`var()`、`@media`、`@import` |
| 类名 | `theme/components.css` 提供一套现成的组件类（`mui-button` 等），也可以完全不用 |
| `${…}` / `data-repeat` / `data-if` | 把 Java 对象、Map 或自定义数据源填进文档 |
| `data-on-click` / `data-on-key` | 把界面上的动作接到 Java 方法上 |
| Java 的 `Mui.screen(…).data(…).on(…).open()` | 装载、绑定、开屏，一行链式调用 |

引擎自身分四层，全部可以脱离游戏运行：

```
HTML → DOM → CSS 层叠 → 盒树 → 布局树 → 绘制列表 → 渲染器
```

**绘制列表**是关键的分界线：布局阶段把"画什么、画在哪"完全定下来（颜色含 `currentColor`、
几何含圆角弧线），渲染器只负责把指令变成调用。所以界面里绝大多数错误在**没有显卡、没有游戏**
的地方就能被发现。

## MUI 不是什么

先把边界说清楚，省得双方浪费时间：

| 没有 | 原因 |
| --- | --- |
| JavaScript / Rhino / KubeJS | 状态住 Java；脚本引擎在 1.7.10 里是安全面、内存面和第二门要调试的语言 |
| Canvas 2D | 没有脚本语言驱动它就没有意义 |
| CSS Grid | flex 覆盖了游戏界面需要的绝大多数布局，Grid 是实现面很大的一个例外 |
| `mask`、`mix-blend-mode`、`filter`、HDR 颜色 | 需要着色器；1.7.10 是固定管线 |
| `float`、`position: sticky`、表格布局 | 有意不做，不是没来得及 |
| 浏览器级一致性 | 目标是"能做出好的游戏界面"的子集，不是 CSS 合规 |
| 静默忽略 | 见下（这是 MUI 唯一一条硬性的产品承诺） |

完整的"没实现清单"（包括每条会打印什么）在 [14 已知限制](14-limitations.md)。

## 一帧里发生什么

作者只要知道这四步，以及它们之间为什么会有边界：

1. **解析（parse）**——HTML 与 CSS 只在文件变了的时候重新解析。
2. **层叠（cascade）**——按选择器匹配、优先级、`!important`、继承算出每个元素的计算样式。
   悬停、按下、焦点、勾选的变化都从这里进入（伪类只在这一步生效）。
3. **布局（layout）**——盒树 → 行盒 / flex 行 / block 流，算出每个盒子的位置与尺寸。
   文字换行也在这里，用的是交给引擎的**文字测量**结果。
4. **绘制（paint）**——生成绘制列表：矩形、网格、渐变、贴图、九宫格边框、文字、裁剪。

**重建由版本号驱动。** 资源层、交互状态、数据绑定、样式表各自持有一个 revision 计数器，
每帧比较一次；任何一个动了，下一帧才重跑。没动就复用上一帧的结果——这是"界面静止时几乎不花时间"
的全部原因。`MuiScreen.rebind()`（[09 动作](09-actions.md)）就是把数据那一半的计数器推一下。

**尺寸一律是逻辑像素。** Minecraft 的 GUI scale 会让 4K 与 1080p 显示器得到同样的逻辑视口，
所以 `@media (max-width: 320px)` 反应的是布局真正拥有的空间，而不是硬件。
`AwtGlyphSource` 会按 GUI scale 用更高的**光栅化倍率**生成字形图集，让放大后仍然清晰，
但字形在逻辑像素里的尺寸不变——否则拖动 GUI scale 滑块会让文字重排。

## 三条设计约定（作者能感觉到的部分）

**一、做不到就上报，不静默忽略。** 每个页面有一份诊断字符串列表。无法识别的属性、读不懂的值、
找不到的样式表、没注册的动作、抛异常的动作，全部写进去。写页面时**第一件该看的东西**就是它
（[13 调试](13-debugging.md)）。

**二、状态住在文档里。** `checked`、`value`、`selected` 是元素属性；引擎写，页面读，
样式表用 `:checked` 选。所以"当前选中了哪一行"可以被绑定、被保存、被恢复，而不是藏在某个
UI 层的私有字段里。

**三、规则只有一处。** "这个控件被禁用了"由一个静态方法回答，样式层、Tab 顺序、方向键、
点击全部问它。一个"这里再多检查一次"就是两条互相矛盾的规则诞生的地方——这条约定是给维护者的，
但它决定了你看到的行为不会自相矛盾。

## 目录与包结构

```
net.misia.misiaui
├── core/          引擎本体，纯 Java，不引用任何平台类型
│   ├── dom/       文档树
│   ├── html/      容错 HTML 解析器
│   ├── css/       选择器、值、简写展开
│   ├── style/     层叠、计算样式、媒体条件、基础样式表、过渡与动画
│   ├── layout/    盒树、block、flex、inline、定位、滚动
│   ├── paint/     绘制指令、圆角网格、绘制列表
│   ├── interact/  命中测试、悬停/按下/焦点、组、表单控件
│   ├── bind/      数据源与绑定
│   ├── res/       资源层、页面装载、重载规则
│   └── text/      字体描述、多行文本的行模型
├── spi/           平台必须实现的缝：文字测量、字形
├── platform/
│   ├── awt/       JDK 字体引擎：测量与字形光栅化
│   └── mc/        1.7.10 渲染器、字形贴图上传、屏幕宿主
├── client/        客户端生命周期接线，以及游戏内自检
└── api/           对外表面：Mui.screen(…).data(…).on(…).open()
```

`core/` 与 `spi/` **不引用 Minecraft、Forge、LWJGL、`java.awt`**——这条规则由
`ArchitectureGuardTest` 扫描源码强制（构建会失败），也就是为什么整套引擎能在毫秒级无头运行、
为什么 `gradlew muiPreview` 不启动游戏就能出图。

`api/` 是唯一故意在平台无关集合之外的包：它是"知道游戏正在运行"的那部分，
用接口把它藏起来只会给使用者多一层间接。

## 怎么确认它是对的

三种证据，缺一不可，**以游戏内截图为准**：

| 证据 | 命令 | 能证明什么 |
| --- | --- | --- |
| 无头测试 | `gradlew muiTest` | 解析、层叠、布局、绘制列表的正确性；几何可以逐行断言 |
| 离线预览 PNG | `gradlew muiPreview` | 不在游戏里也能**看图**，且每张图旁边有绘制列表与盒树 |
| 游戏内自检截图 | `gradlew runClient -PmuiSelfTest=…` | 真实渲染器：Tessellator、批次、字形贴图、`glScissor`、GUI scale |

离线预览是一个**预测**：它用 Java2D 重放同一份绘制列表，快、而且可以在自己掌控的时钟上取任意瞬间，
但它不是答案。看起来对而游戏里不对的页面就是错的，"预览一致"不算修复。历史上三个 bug
（三角形绕序、贴图绑定早于开启批次、字形亚像素位置）只有在真客户端里才看得见。
